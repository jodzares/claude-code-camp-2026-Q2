The model

Reads an English question and decides what to do next.

Can touch nothing. No filesystem, no network, no MUD.
SO THEY TAKE TURNS

My machine

Owns the filesystem, the network, the MUD connection.

Cannot choose. It only runs what it is told to run.

Two actors, and only one boundary between them. Everything in this document is either something happening on one side of that boundary, or something crossing it. There are only two crossings in the whole trip.

Part oneWhy this isn't circular

The first time I saw this loop it looked pointless. Why ask the model to list a directory, when listing a directory is something my own machine has to do anyway? If I'm doing the work regardless, what is the model for?

Because I never asked for a listing. I asked an English question and handed over a menu of things I am willing to do. The model decided that a listing was the way to answer it, and decided which folder to list.

For one trivial question I could have written those steps myself. For a real question I can't: which folder, which file, and whether one read is even enough all depend on results that don't exist at the moment I ask.

The division of labour, in one line.

The model decides what to do next, from the question and everything it has seen so far. My machine acts, because it is the only one that can. That back-and-forth — ask, run, report, continue — is the whole idea.

Part twoThe scenario

One scenario runs through this entire document. It never changes.

I ask: "Is there anything in my notes about the dragon?" My notes folder holds three files: quests.md, bestiary.md, shopping.md. My program offers the model two things it is allowed to ask for: read a file, or list a directory.

One honest note about this scenario. The example file that actually ships in my repo asks a duller question — "What files are in the current directory?" — with those same two tools [week1_baseline/ruby/04_api_client/examples/example.rb]. I've swapped in the dragon question because it needs two tools in sequence rather than one, which is what makes the loop visible. Everything else on this page — the settings, the model name, the system prompt, the tool descriptions, the shape of the request and the reply — is real and taken from my own files.

Part threeThe cast, before anything moves

Every name used later, defined once here, in the order each thing comes into existence. Nothing in this list acts yet. They are just the parts on the table.

the settings file
A small text file of choices I am allowed to change without touching anyone's code: which provider, which model, whether to use my own prompt. It is committed to the repo and travels with it. [.boukensha/settings.yaml]
the secrets file
A separate file holding the one thing that must never reach a public repo: my API key, the password-like string that proves the request is mine and gets me billed for it. Deliberately hidden from version control. [.boukensha/.env]
the config
The component that boots first and reads both those files once, then hands values out to whoever asks. One door in, one answer out — so nothing in the program disagrees about what the settings say. [config.rb]
the task
One named role the program can play, with its own provider, model and prompt. Today there is exactly one, called player. The nesting exists so a second role can be added later without renaming anything. [tasks/player.rb]
the system prompt
A standing instruction sent with every request, telling the model who it is being. Mine says: "You are my MUD jodza-player." It is resolved by a ladder — if I switched the override on and my file exists, mine is used; otherwise the one shipped with the code. [.boukensha/prompts/player/system.md]
the context
The memory of one run. It holds three things: the system prompt, the list of messages so far, and the table of tools on offer. It stores; it never acts. [context.rb]
a message
One turn in the conversation: who said it, and what was said. The who is called the role — me, the model, or the result of a tool. [message.rb]
a tool
One thing my program is willing to do, described in two halves. The half the model sees: a name, a sentence of description, and the list of arguments it accepts. The half the model never sees: my actual code that does the work. [tool.rb]
the registry
The component that builds a tool and files it into the context's table in one move, so it is impossible to build one and forget to file it. It also knows how to look a tool up by name and run it — although nothing calls on that ability yet. [registry.rb]
the provider
A single word in the settings file naming which vendor to talk to. Mine says anthropic. It is a word, not a file — the trap I fell into twice.
an adapter
One file per vendor, holding everything specific to that vendor: its web address, its headers, its exact request shape, and the list of models it accepts. Five exist; exactly one is built per run. [backends/anthropic.rb]
the builder
The component that knows no vendor at all. It holds the context and one adapter, and forwards five fixed questions to that adapter: format the messages, format the tools, assemble the whole request, what headers, what address. Those five questions are the contract — a vendor is supported exactly when some adapter can answer all five. [prompt_builder.rb]
the client
The newest component, and the only one that touches the network. It holds one thing — the builder — asks it for the address, the headers and the body, sends them, retries what is worth retrying, and hands back what came home. It never learns the word anthropic. [client.rb]
the runner
The file I actually execute. It is the assembly point: it creates all of the above in order, adds the question, and prints whatever comes back. [examples/example.rb]
the launcher
A two-line shortcut that steps into the module's folder and starts the runner with that module's own dependency list. [week1_baseline/bin/ruby/04_api_client]

Count the columns.

Twelve steps on my side before anything leaves. Four on the model's. And exactly two crossings.

That asymmetry is the point of four whole lessons. Config, the three shapes, the registry, the builder and the client all exist so that one arrow crosses that line correctly, carrying the right thing, in the shape one particular vendor demands.

Part fiveBoot — everything before the crossing

Where we are t0–t11 my machine · boot
t12 crossing out · t13–t16 the model · t17 crossing back · t18–t19 my machine · t20+ not built

Steps t0 to t11 all happen on my machine, in that order, and the order is forced — each step needs the one above it to have finished.

The config must be first, because the prompt, the provider and the model all come out of it. The context must exist before the tools, because the tools are filed into it. The adapter must be built before the builder, because the builder is handed one and never goes looking. The builder must exist before the client, because the client holds nothing else.

The single most useful fact about this whole stretch: none of it costs anything. Nothing has left the machine. A completely fake API key would have passed every one of these twelve steps. That is why the previous three lessons could be built and tested without ever spending a penny — and it is exactly what changes at t12.

What the two tools look like at t6

Each tool is declared with a name, a sentence of description, and the arguments it accepts. Note what is not here: any actual value.

The menu, as declared in the runner

name: "read_file" description: "Read the contents of a file from disk" accepts: path — text — "The file path to read" name: "list_directory" description: "List files in a directory" accepts: path — text — "The directory path to list"

I declared that list_directory takes a path. I did not say which path, because at the moment I write that line I don't know what anyone will ask for. Filling that blank is the model's job, and it is the single most important thing it does.

Part sixCrossing one — what actually leaves

Where we are t0–t11 my machine · boot
t12 crossing out · t13–t16 the model · t17 crossing back · t18–t19 my machine · t20+ not built

The client asks the builder three questions and gets three answers, all of which the builder obtained from the Anthropic adapter. Then it sends them.

Answer one — the address

https://api.anthropic.com/v1/messages

Answer two — the headers

Content-Type: application/json x-api-key: (my secret key, from the secrets file) anthropic-version: 2023-06-01

Headers are the labels on the envelope rather than the letter inside: what format this is, who is sending it, which version of the vendor's rules to apply. This is where the key rides, and it is the reason the secrets file must never reach a public repo.

Answer three — the body, sent to the address above

{
  "model": "claude-haiku-4-5",
  "system": "You are my MUD jodza-player",
  "max_tokens": 1024,

  "tools": [
    { "name": "read_file",
      "description": "Read the contents of a file from disk",
      "input_schema": {
        "type": "object",
        "properties": {
          "path": { "type": "string",
                    "description": "The file path to read" } },
        "required": ["path"] } },

    { "name": "list_directory",
      "description": "List files in a directory",
      "input_schema": {
        "type": "object",
        "properties": {
          "path": { "type": "string",
                    "description": "The directory path to list" } },
        "required": ["path"] } }
  ],

  "messages": [
    { "role": "user",
      "content": "Is there anything in my notes about the dragon?" }
  ]
}

Read it as three things bundled together. system is who the model is being. messages is the conversation, currently one line long. tools is the menu. One send, all three together — the model cannot ask for a menu later.

The envelope is theirs. The contents are mine.

The field names in that request are fixed by the vendor. Rename tools to functions and the request is rejected outright.

What goes inside those fields is entirely mine. Calling the tool file_reading instead of read_file works perfectly. Calling it tool_2 with no description also works, and chooses badly, because the model has nothing to judge from. Tool names and descriptions are prompt text, not documentation.

Part sevenThe model's side

Where we are t0–t11 my machine · boot · t12 crossing out
t13–t16 the model · t17 crossing back · t18–t19 my machine · t20+ not built

Four steps, and my machine is idle for all of them. The model reads the standing instruction, reads my question, reads the two descriptions, and makes two decisions: which tool, and what argument.

The second decision is the one worth staring at. The value "notes" appears nowhere in my code. It was produced from my English sentence — I said "my notes", and it turned that into a folder name — constrained only by the shape I declared, which said this argument must be text. Ask a different question and the same tool comes back with a different value.

And it ran nothing. It cannot. It asked, by name, with an argument it chose, and then stopped.

Part eightCrossing two — what comes back

Where we are t0–t11 my machine · boot · t12 crossing out · t13–t16 the model
t17 crossing back · t18–t19 my machine · t20+ not built

The reply, as it arrives

{
  "role": "assistant",
  "content": [
    { "type": "text",
      "text": "Let me check what's in your notes." },

    { "type": "tool_use",
      "id": "toolu_01H1b2...",
      "name": "list_directory",
      "input": { "path": "notes" } }
  ],
  "stop_reason": "tool_use",
  "usage": { "input_tokens": 651, "output_tokens": 65 }
}

Three signals in that reply, and they do different jobs.

stop_reason: "tool_use"
The flag. The model stopped mid-answer on purpose, because it needs a result before it can continue. This is not an error and not a failure. The alternative value is end_turn, meaning finished.
the tool_use block
The detail. Which tool, which argument it filled in, and an identifier I must quote when I send the result back so the model can match my answer to its question. The flag says something is wanted; this block says what. They arrive in the same reply, so nothing is hidden and nothing needs a second request to discover.
usage
What the exchange cost, counted in tokens — the chunks of text a model is billed by, roughly three-quarters of a word each.

What my code does with all that: nothing

At t18 the client converts the whole reply into data I could reach into by name, and stops there. It pulls nothing out. At t19 the runner prints it and the process ends.

This is the correct stopping place, and it is deliberate. Had the client extracted "the answer" here — reaching for the text of the first block — it would have kept "Let me check what's in your notes" and thrown away the instruction sitting in the second block, along with the flag and the cost. On a reply where the model calls a tool and says nothing at all, that extraction would have produced an empty result from a perfectly good reply.

Part nineWhere this is going

Where we are t0–t11 my machine · t12 crossing out · t13–t16 the model · t17 crossing back · t18–t19 my machine
t20 onwards — not built

Nothing in this part exists in my repo. It is here because the two parts above make no sense without it — a flag nobody reads and an identifier nobody quotes are only meaningful once something uses them.

The steps below the amber marker close the loop: notice the flag, run the tool, report the result, send everything again. That produces a second trip through the same two crossings, and then a third.

Trip two — the model chooses again, with new information

out the whole conversation again, now four items long: my question · the menu · the model's request · my result ["quests.md", "bestiary.md", "shopping.md"] model reads the file list, picks a DIFFERENT tool: read_file fills path = "notes/bestiary.md" back stop_reason: "tool_use" → loop continues

That path could not have existed one trip earlier. The model only knew the file was called bestiary.md because my machine listed the folder and told it.

Trip three — enough information, so it answers

out the whole conversation again, now including the file's contents model has enough. No tool needed. back stop_reason: "end_turn" text: "Yes — bestiary.md says the dragon guards the eastern gate." → LOOP ENDS

The conversation grows every trip; the model remembers nothing.

The whole history is re-sent each time — the original question, every tool request, every result. Between calls the model retains nothing at all. The context on my side is the only memory in the system. That is why the context was built before anything that talks to a model, and why it grows rather than being replaced.

The exit is end_turn.

Trips repeat for as long as the flag says tool_use. The first end_turn stops the loop. That single comparison is the difference between a program that asks once and an agent that works until it is done.

One string has to match on both sides.

The reply says "list_directory". My code will look up exactly that text in the registry. Rename the tool on one side only and the lookup finds nothing — and the registry stops loudly with a named error rather than quietly pretending it worked.

Part tenWhy each shape is that shape

Five components, five decisions. Each one has a real cost, listed honestly.

The settings live outside the code

00 Config · t1–t3

Two different reasons, one mechanism. My API key must never reach a public repo, or I lose money. My model choice must be changeable without editing anyone else's source. So both are exiled into files — but into different files, split by one question: does this get committed to the repo, or hidden from it?

The cost: the prompt ladder falls through silently. If the override switch is off, or my file is misnamed by one character, the shipped default is used and the run prints a perfectly happy result. I only catch it by noticing the wrong prompt in the output.

The tool table lives on the context, not the registry

01 Struct Skeleton · 02 The Registry · t4–t6

The context is the memory of the run, and the tools are part of what the model must be told, so they belong in the memory alongside the messages. The registry holds only a pointer to that one context and files through it.

Splitting them the other way would give two owners of the same table, and two owners drift apart.

The cost: the boundary is smudged — the registry can file a tool, but so can the context directly. Andrew flags this as untidy and leaves the clean split for later.

Five adapters, not one component that knows five vendors

03 Prompt Builder · t8–t9 · the money shot

Every vendor wants the same conversation in a differently shaped envelope. That knowledge could live in one component branching five ways at every step, or in five small components that each know exactly one vendor.

Five wins, for a reason sharper than tidiness: vendors disagree about position, not just naming. My system prompt sits in its own top-level slot for Anthropic. For OpenAI it has to become the first entry inside the message list, making that list four items long instead of three. A table of renamings can change a label; it cannot move an item into a list. That is why each adapter assembles its own envelope from scratch.

The cost: three of the five adapters carry identical tool-formatting code, and the five-question contract isn't actually enforced anywhere — it is a convention the five happen to keep.

The client holds the builder, and nothing else

04 API Client · t10–t11

To send anything you need three facts: address, headers, body. All three are vendor-specific and all three already have an owner. So the client holds the one component that can answer all three, asks it the same three questions every run, and never learns which vendor it is talking to.

Holding the adapter directly would mean holding two things instead of one, because the body cannot be built from vendor knowledge alone — it needs the conversation too.

The cost: the client is useless without a builder. There is no way to push a hand-written request through it.

Nothing prewritten does the sending

04 API Client · t12

A vendor's own prewritten library would do the sending and hide how. Doing it by hand means the exact bytes leaving my machine are in a file I can open. With five vendors that is five libraries that disagree with each other — Anthropic's own ships in two languages that don't have matching features — so "use the library" is not one answer, it's five answers with five different holes. It is also a hard constraint of this project.

The cost is real and I hit it. Libraries quietly locate the files my machine uses to verify a secure website is genuine. By hand, I have to point at those files, and they sit in different places on macOS and on WSL2. The shipped code solves it by pointing at nothing and letting the operating system answer the question about itself. Verification stays switched on; only the hard-coded path is dropped.

Part elevenGlossary

adapter
One file holding everything specific to a single vendor. Also called a backend in the code.
agent loop
The repeating cycle of ask, run, report, continue, until the model says it is finished. Not built yet.
API key
A secret string that proves a request is mine and gets me billed for it.
argument
A value handed to a tool when it runs. Here, the folder or file path.
backoff
Waiting longer before each retry, so a struggling server is not hammered. Mine waits half a second, then one, then two.
context
The memory of one run: the standing instruction, the messages so far, and the tool table.
dispatch
The act of looking a tool up by name and running it. An action, not a thing.
endpoint
The exact web address a request is sent to.
environment variable
A named value the operating system hands a program at startup, set outside the code.
headers
Labels on the envelope rather than the letter inside: format, identity, version.
JSON
A common text format for structured data — labelled fields, lists, and nesting.
message
One turn in the conversation: who said it and what was said.
navigable data
Text converted into a structure whose parts can be reached by name.
payload
The body of a request — the actual letter inside the envelope.
POST
Sending a body to a web address and waiting for a reply.
provider
A word in the settings naming which vendor to use. A word, not a file.
registry
The component that builds and files tools, and can run one by name.
retry
Sending the same request again after a failure that might not repeat.
role
Who a message came from: me, the model, or the result of a tool.
runner
The file I actually execute; the assembly point for everything else.
schema
A declaration of what arguments a tool accepts and what type each one is. It declares the blanks; the model fills them.
stateless
Holding nothing between calls. The model is stateless between requests, which is why the whole conversation is re-sent every trip.
status code
The number in a reply meaning fine, or a named kind of not-fine: wrong key, too fast, server busy.
stop_reason
The flag in a reply saying why the model stopped. Either it wants a tool run, or it is finished.
system prompt
A standing instruction sent with every request, telling the model who it is being.
token
The chunk of text a model is billed by — roughly three-quarters of a word.
tool
One thing my program is willing to do: a description the model sees, and code the model never sees.
YAML
A plain-text format for settings, using indentation to show what belongs inside what.
